# Phase 7.2 演化工作区功能与界面规划

> 文档状态：已确认实施基线；开发中
> 编制日期：2026-08-14
> 适用范围：`预览与追踪`、`阶段与分支`、`历史记录`三个窗口，以及它们与`演化方案`的衔接
> 当前状态：Schema v17、统一工作台、可追踪运行、提交草稿、四类目标事务入口及演化图已经进入实现；正式结项仍以自动总验收和独立 Windows 人工验收为准

## 1. 先用一句话说明三个窗口

- **预览与追踪**：回答“这次演化把哪些词变成了什么，为什么会这样”。
- **阶段与分支**：回答“确认结果后，要把它保存到哪个历史阶段、方言或后代语言”。
- **历史记录**：回答“过去运行过什么、使用了哪个方案、提交到了哪里，以及能否复现”。

它们组成一条明确的工作流：

```text
演化方案
  编写规则、选择参与演化的词、保存方案版本
        ↓
预览与追踪
  运行规则、检查结果、查看逐步变化和错误
        ↓
阶段与分支
  选择落点、处理冲突、一次性正式提交
        ↓
历史记录
  回查、复现、比较、继续未提交的运行
```

原则是：**预览不会修改正式词典；只有“阶段与分支”的最终确认才会写入正式项目数据。**

## 2. 本阶段的产品边界

### 2.1 Phase 7.2 要完成

1. 一个语言可以保存多个命名的演化方案。
2. 方案编辑后 3 秒自动保存工作草稿，并可建立不可变的版本快照。
3. 用户可以从当前阶段词典中筛选并勾选参与演化的词。
4. 每次运行都保存完整输入、规则版本、引擎版本、结果、错误和追踪信息。
5. 运行结果可以提交为：
   - 当前语言的新历史阶段；
   - 当前语言已有的后续历史阶段；
   - 已有且可承载数据的方言；
   - 一个新的后代语言。
6. 正式提交必须原子化：全部成功或全部不写入，并且形成一个全局撤销步骤。
7. 三个窗口之间保留当前方案、运行、筛选和选中行，不因切换窗口丢失工作位置。

### 2.2 本阶段明确不做

- 不做逆向祖语重构。
- 不做概率演化和词频参与计算；这属于 Phase 7.4。
- 不把标签作为组合筛选条件；标签属于 Phase 7.3，Phase 7.2 只预留数据接口。
- 不允许 AI、Lexurgy 或 Analysis Sidecar 直接提交正式数据。
- 不在本窗口新建方言类型；如需新方言，先在“方言”页面建立，再作为演化落点。
- 不用可点击的假入口提前展示尚未实现的功能。

## 3. 四类核心数据及其关系

为了让自动保存、复现和全局撤销彼此不冲突，Phase 7.2 将“可编辑草稿”和“不可变证据”分开。

| 数据                            | 是否可修改 | 用途                                         |
| ------------------------------- | ---------- | -------------------------------------------- |
| 演化方案 `EvolutionPlan`        | 是         | 用户持续编辑的工作草稿，如“第一次辅音推移”   |
| 方案版本 `EvolutionPlanVersion` | 否         | 某一时刻的规则、测试词和设置快照             |
| 演化运行 `EvolutionRun`         | 否         | 某个版本对一批确定输入的实际运行结果与追踪   |
| 演化提交 `EvolutionDelivery`    | 否         | 某次运行被提交到哪个阶段或语言、如何处理冲突 |

每次点击“运行预览”时：

1. 如果当前草稿与最近版本不同，先自动建立一个方案版本；
2. 固定来源阶段和用户勾选的词条；
3. 保存完整输入快照和来源状态校验值；
4. 调用引擎运行；
5. 将成功、失败或取消状态都写入运行记录。

这样，未来点击“按原输入重新运行”时，使用的是当时真正的规则和词条，而不是后来已经修改的词典。

## 4. 窗口一：预览与追踪

### 4.1 窗口目标

让用户先理解并检查演化结果。该窗口只处理“结果是什么、为什么”，不选择项目谱系，不写正式词典。

界面名称沿用项目现有文案 **“预览与追踪”**；它与“预览和追踪”含义相同，但可以避免同一功能出现两种名称。

### 4.2 桌面布局

```text
┌ 预览与追踪 ───────────────────────────────────────────────┐
│ [运行：2026-08-14 14:32 ▾]  方案 v3  来源：古语·早期       │
│ 120 个输入｜86 个变化｜30 个未变化｜2 个警告｜2 个错误     │
│ [搜索词形…] [全部状态 ▾] [全部冲突 ▾]   [按当前内容重跑]    │
├──────────────────────────────┬─────────────────────────────┤
│ 结果表                       │ 所选词追踪                  │
│ 来源词  →  结果词  状态      │ *pata → fada                │
│ pata    →  fada    已变化    │ 1. p > f / #_    pata→fata │
│ kata    →  kata    未变化    │ 2. t > d / V_V   fata→fada│
│ ...                          │ [显示未命中的规则]          │
│                              │ 中间阶段、警告、错误详情     │
├──────────────────────────────┴─────────────────────────────┤
│                                             [进入阶段与分支]│
└────────────────────────────────────────────────────────────┘
```

- 左侧是可排序、可筛选的结果表；超过 50 行时使用虚拟列表，避免大型词典卡顿。
- 右侧是当前选中词条的检查器，不再把追踪 JSON 作为主要阅读方式。
- 主内容宽度不足时，右侧检查器移到结果表下方；不得产生页面级横向滚动。
- 底部只有一个主要动作：“进入阶段与分支”。

### 4.3 顶部运行摘要

顶部第一行选择要查看的运行，并显示：

- 运行时间与状态；
- 方案名称和版本号；
- 来源语言与来源阶段；
- 参与运行的词条总数；
- 已变化、未变化、警告、错误数量。

数量同时使用文字和图标，不能只依赖红、黄、绿颜色表达状态。

### 4.4 结果表

默认列为：

| 列       | 内容                                     |
| -------- | ---------------------------------------- |
| 来源词形 | 运行前保存的词形，不随当前词典变化       |
| 结果词形 | 引擎原始输出；人工修订时同时显示修订标记 |
| 变化状态 | 已变化、未变化、警告、错误               |
| 规则步数 | 实际改变词形的规则数量                   |
| 冲突     | 输出碰撞、空结果、非法结果等             |

支持搜索来源词形和结果词形，并支持：全部、已变化、未变化、警告、错误筛选。筛选条件与当前运行写入窗口状态，切换标签后返回仍然保留。

### 4.5 单词追踪检查器

选择一行后，右侧按顺序展示：

1. 原始输入；
2. 每条实际命中的规则；
3. 每一步的变化前后；
4. 中间阶段结果；
5. 最终引擎输出；
6. 警告或错误及修复建议。

默认只显示真正造成变化的规则。用户可以勾选“显示未命中的规则”进行专家检查，但该设置不改变运行结果。

如果允许人工修订结果，系统必须同时保留：

- `engineOutput`：引擎原始结果，永不覆盖；
- `resolvedOutput`：用户准备提交的修订结果；
- 修订人、时间和原因。

### 4.6 冲突与错误分级

| 等级       | 示例                                       | 是否可以进入下一窗口       |
| ---------- | ------------------------------------------ | -------------------------- |
| 阻断错误   | 引擎崩溃、空词形、非法结构、输入快照损坏   | 否                         |
| 待处理冲突 | 多个来源词演化成同一词形、与落点已有词冲突 | 可以进入，但提交前必须处理 |
| 警告       | 某词未命中任何规则、存在可疑字符           | 可以                       |
| 信息       | 词形无变化                                 | 可以                       |

错误必须出现在相关行和检查器中，并写清“发生了什么、如何继续”，不能只显示“运行失败”。

### 4.7 重新运行的两个动作

- **按原输入重新运行**：使用历史版本和历史输入，用于验证能否复现。
- **按当前内容重新运行**：使用当前方案草稿与当前词典重新生成一个新运行。

两个动作不能合并成含义模糊的“重新运行”。旧运行始终保持不变。

### 4.8 状态设计

- 没有运行：说明“先在演化方案中选择词条并运行预览”，提供“返回演化方案”。
- 运行中：300 毫秒内不闪烁加载提示；超过 300 毫秒显示真实进度和“取消运行”。
- 已取消：保留取消记录和已知诊断，但不能提交。
- 运行失败：保留错误记录，提供“返回修改方案”和“重试”。
- 运行成功但有阻断错误：可检查结果，禁用提交按钮并在按钮旁说明原因。

## 5. 窗口二：阶段与分支

### 5.1 窗口目标

把已经检查过的运行结果安全地放入项目时间线或谱系。该窗口负责选择落点、汇总冲突和正式提交。

### 5.2 桌面布局

```text
┌ 阶段与分支 ───────────────────────────────────────────────┐
│ 运行：第一次辅音推移 v3 · 120 个词 · 已检查              │
├──────────────┬──────────────────────────┬─────────────────┤
│ 保存为       │ 落点设置                 │ 提交影响        │
│ ● 新历史阶段 │ 名称 [中古语……]          │ 新增阶段 1      │
│ ○ 已有阶段   │ 时间父级 [早期 ▾]        │ 更新词条 120    │
│ ○ 已有方言   │ 日期/说明/记录状态       │ 新增关系 1      │
│ ○ 后代语言   │                          │ 待处理冲突 2    │
│              ├──────────────────────────┤                 │
│              │ 冲突汇总表               │ [确认并提交]    │
└──────────────┴──────────────────────────┴─────────────────┘
```

- 左侧是紧凑的输出类型列表，不使用四张大卡片。
- 中间只显示当前输出类型需要填写的字段，并在下方集中处理冲突。
- 右侧固定显示本次操作会新增、修改和关联多少数据。
- 每个屏幕只有一个主要按钮：“确认并提交”。

### 5.3 四种输出类型

#### A. 当前语言的新历史阶段

适合把来源阶段向后推进一步。

必填内容：阶段名称、时间父级、数据基础、记录状态；可选内容：日期范围和说明。

- 来源阶段保持不变。
- 新阶段采用 `inherited_delta`，通过继承加差异解析为完整状态。
- 承载演化数据的阶段不能标记为 `no_data`。
- 时间父级与数据基础继续保持为两个独立关系。

#### B. 当前语言的已有后续历史阶段

适合用户已经预先建立目标阶段的情况。

- 目标必须属于同一语言；
- 目标必须能承载数据，`no_data` 阶段不可选；
- 目标必须位于合理的后续时间位置；
- 提交前汇总目标词典已有修改造成的冲突。

#### C. 已有方言

适合把结果写入项目中已经建立、并且与来源数据基础兼容的方言。

- 只列出可承载数据且谱系关系有效的方言；
- 不兼容的方言不静默隐藏，而是禁用并说明原因；
- 创建新方言仍在“方言”页面完成。

#### D. 新的后代语言

一次操作内创建：

1. 新语言；
2. 不可删除的内部默认状态；
3. 首个可见历史阶段；
4. 与来源语言的主要谱系关系；
5. 完整、可使用的目标词典；
6. 来源运行、版本和词条级出处证据。

对于没有参与演化的词，默认按来源状态原样继承，不能丢失。对于包含语素关联的词条，语素及关系必须一起复制并重新映射；没有事务级复制支持的组件不得用一个看似可用的勾选项冒充已实现能力。

### 5.4 冲突汇总与处理

所有冲突一次性汇总，不逐个弹窗打断用户。典型冲突包括：

- 多个来源词得到同一结果词形；
- 结果词形与目标已有词条相同；
- 来源或目标在预览后已被修改；
- 阶段名称、日期或谱系关系无效；
- 目标阶段无法承载数据。

词条冲突可按实际情况提供：保留现有、使用新结果、合并义项、建立同形词、手动编辑、跳过。危险选项默认不选中，并显示提交后的实际差异。

未登记音不通过一个无明细的“确认”按钮直接放行。工作台为每个新增音保存结构化音系决定：用户选择独立音位或音位变体；变体必须指定所属音位；分布/条件优先从逐规则追踪对应的 Lexurgy 规则预填，缺少规则证据时使用实际结果中观察到的环境并明确标注。用户可以修订预填内容，保存决定时工作台自动重新检查。正式提交才把这些音系差异与词典、阶段或后代语言一起原子写入，同一个全局操作负责失败回滚、撤销与重做。

如果来源状态校验值或目标状态校验值已经改变，系统阻止提交并提示重新运行或重新检查，绝不把旧预览静默提交到新数据上。

### 5.5 提交确认

最终确认弹窗必须用项目语义色令牌同时适配浅色和深色模式，并显示：

- 来源语言与阶段；
- 目标类型与目标名称；
- 新增、更新、跳过的词条数量；
- 新增阶段、语言和关系数量；
- 已解决与未解决冲突数量。

确认后由应用服务执行一项项目操作。任意一步失败时全部回滚，不能留下“语言已创建但词典只有一半”等中间状态。

提交成功后提供两个明确去向：“打开目标”和“查看历史记录”。

### 5.6 全局撤销语义

- 一次演化提交对应一个全局撤销步骤。
- 撤销新历史阶段会撤销本次产生的阶段、差异数据和出处关系。
- 撤销新后代语言会撤销本次原子创建的整组数据。
- 若提交后相关记录已被后续操作修改，沿用 Phase 7.1 的冲突保护，不能强行覆盖。
- 重做恢复完全相同的提交结果，不重新调用引擎。

## 6. 窗口三：历史记录

### 6.1 窗口目标

提供演化领域的可复现审计记录。它与“编辑 → 项目历史”不同：

- “项目历史”负责撤销和重做整个项目的写操作；
- “演化历史记录”负责查看方案版本、运行证据和提交去向。

窗口顶部会用一句帮助文字说明这一区别。

### 6.2 桌面布局

```text
┌ 历史记录 ─────────────────────────────────────────────────┐
│ [搜索…] [全部方案 ▾] [全部类型 ▾] [全部状态 ▾] [日期 ▾]   │
├────────────────────────────────┬───────────────────────────┤
│ 时间      类型  方案/版本      │ 记录详情                  │
│ 14:35     提交  辅音推移 v3    │ 来源、输入、规则校验值    │
│ 14:32     运行  辅音推移 v3    │ 引擎版本、结果、错误      │
│ 13:08     版本  辅音推移 v2    │ 提交目标、冲突决定        │
│ ...                            │ [查看预览] [复现] [...]   │
└────────────────────────────────┴───────────────────────────┘
```

历史使用紧凑表格而不是装饰性时间线；大量记录下更容易搜索、比较和定位。

### 6.3 记录类型

| 类型     | 记录内容                                       |
| -------- | ---------------------------------------------- |
| 方案版本 | 规则、测试词、设置、版本说明、内容校验值       |
| 运行     | 来源阶段、输入快照、引擎版本、结果、追踪、错误 |
| 提交     | 目标、冲突决定、创建或修改的数据、项目操作编号 |

失败和取消的运行也会保留，因为它们有助于解释“为什么没有得到结果”。

### 6.4 筛选与详情

筛选包括：关键词、方案、记录类型、状态和日期范围。表格默认按时间倒序，日期与数字使用本地化格式和等宽数字，避免列宽跳动。

右侧详情根据记录类型显示：

- 方案版本：完整规则快照、测试词、版本说明、校验值；
- 运行：确切输入、引擎及协议版本、结果统计、逐词追踪和错误；
- 提交：目标位置、冲突处理决定、创建记录清单、对应的全局操作编号。

### 6.5 可执行动作

- **在预览与追踪中打开**：查看该运行的逐词结果。
- **继续提交**：成功但尚未提交的运行进入“阶段与分支”。
- **按原输入复现**：以历史版本和历史输入创建一个新运行，并比较校验值。
- **按当前内容重跑**：以当前词典和当前方案草稿创建新运行。
- **复制为新草稿**：从旧版本建立一个新工作草稿，不修改旧版本。
- **打开目标**：已提交记录跳转到对应语言或阶段。

历史详情可以说明某个提交是否仍可通过全局历史撤销，但不在这里另造一套撤销系统。只有全局历史中仍满足顺序和冲突条件的操作才能撤销。

### 6.6 保存与清理规则

- 已产生正式提交的版本、运行和提交记录不可删除。
- 未提交的成功、失败或取消运行可以由用户手动清理；清理前确认，并作为一个可撤销的项目操作。
- 不设置会静默删除证据的自动过期策略。
- 项目打开时只读取记录摘要；选中一条后再读取大型追踪内容，避免历史越多启动越慢。

## 7. “演化方案”需要同步调整的部分

虽然本文件重点是三个新窗口，但它们依赖“演化方案”提供可靠输入。

### 7.1 多方案与版本

- 左上提供方案选择器、新建、重命名、复制和删除。
- 删除有历史运行或提交引用的方案时，只归档方案，不删除历史证据。
- “保存版本”建立明确检查点；运行时如有未版本化修改，则自动建立版本。

### 7.2 自动保存与全局历史

- 用户停止编辑 3 秒后自动保存工作草稿。
- 连续编辑使用同一个合并键写入项目历史：全局撤销一次撤回一段连续编辑，而不是逐字撤回每次自动保存。
- 切换方案、手动建立版本或开始运行时结束当前连续编辑段。
- 保存失败时保留编辑器内容，紧邻编辑区域显示失败原因和“重试”，不得显示虚假的“已保存”。

### 7.3 输入词条选择

Phase 7.2 支持：

- 搜索词形和释义；
- 按词性、词条状态、来源类型筛选；
- 选择当前结果、反选当前结果、清空选择；
- 切换筛选后保留已经勾选的词；
- 显示“当前结果已选数量 / 总已选数量”。

测试词与正式词典输入严格分开。测试词可以直接执行不读取词典的临时 Lexurgy 试跑，但不创建方案版本、正式运行或提交记录，也不能被误提交到目标词典。

标签筛选和词频筛选分别等 Phase 7.3、7.4 提供真实字段后再出现。

## 8. 共同的界面与可访问性规则

1. 继续使用 `design-system/fishtongue/MASTER.md` 的语义令牌；所有表面、边框、文字、焦点、警告和弹窗必须分别验证浅色与深色模式。
2. 保持全窗口桌面布局；参考尺寸 `1440 × 900`，最低验收尺寸 `1280 × 800`。
3. 使用现有图标家族，图标按钮必须有中文和英文可访问名称；不用 Emoji 作为结构图标。
4. 标签页、表格、单选、复选和弹窗使用语义化控件并支持完整键盘操作；焦点顺序与视觉顺序一致。
5. 长词形、长阶段名和长错误信息必须换行或省略并可查看全文，不能撑破布局。
6. 运行、提交等异步状态使用 `aria-live="polite"`；错误放在对应区域或字段旁。
7. 高频标签切换不做位移动画；只使用已有的短颜色/透明度反馈，并遵守 `prefers-reduced-motion`。
8. 标签、筛选、当前运行和展开检查器应进入可恢复的窗口状态；页面返回时恢复滚动位置。
9. 原生下拉框必须显式使用主题表面色和文字色，避免 Windows 深色模式出现白底白字。
10. 所有列表空状态都说明原因并给出下一步，不显示空白面板。

## 9. 技术实施边界

数据流保持：

```text
React UI
  → Application Service
    → Repository
      → Tauri SQL Plugin
        → SQLite
```

- React 只收集用户选择和展示结果，不直接执行 SQL，也不在页面中编排多表事务。
- Lexurgy Sidecar 只负责按确定输入运行；Tauri 继续负责启动、健康检查、超时、取消和退出清理。
- Repository 保存不可变版本、运行和提交，并提供按摘要分页、按需加载追踪的查询。
- 所有正式写入经过 Phase 7.1 的项目操作协议；失败恢复最后一个可用项目状态。
- Schema v17 只新增和迁移，不删除旧 Phase 5 演化批次证据。

### 9.1 建议的 Schema v17 实体

| 表                        | 关键内容                                          |
| ------------------------- | ------------------------------------------------- |
| `evolution_plans`         | 命名方案、工作草稿、归档状态、草稿版本号          |
| `evolution_plan_versions` | 不可变规则与设置快照、校验值                      |
| `evolution_runs`          | 版本、来源、状态、引擎版本、输入/来源校验值、摘要 |
| `evolution_run_items`     | 每个词的输入、引擎输出、修订输出、追踪和错误      |
| `evolution_deliveries`    | 运行、目标、冲突决定、项目操作编号和提交摘要      |

逐词结果采用独立行，而不是把整个大型运行塞入一个 JSON 字段；这样才能分页、筛选并只加载当前词的追踪。

### 9.2 旧项目迁移

- 旧版每语言单一 `Evolution` 迁移为“默认方案”，保留原规则和测试词。
- 旧 Phase 5 阶段演化批次继续可读；迁移建立兼容引用或只读映射，不删除旧表和原始证据。
- 迁移前备份项目；任何失败都不得覆盖最后一个可用 `.fishtongue` 文件。
- 新旧项目必须运行同一套待处理迁移，不能只修新建项目。

## 10. 建议开发顺序

### 第 1 组：模型、迁移和仓储

1. 定义方案、版本、运行、逐词结果和提交模型。
2. 实现 Schema v17 与旧项目迁移。
3. 建立摘要分页、按需追踪读取和完整复现查询。
4. 将草稿自动保存合并到一个连续编辑历史步骤。

### 第 2 组：演化方案输入

1. 多方案管理和版本快照。
2. 3 秒自动保存、失败恢复和保存状态。
3. 词典搜索、基础筛选和跨筛选选择。
4. 运行前建立确定性输入快照。

### 第 3 组：预览与追踪

1. 运行状态机、取消和错误保存。
2. 结果表、状态筛选和虚拟列表。
3. 逐规则追踪检查器、中间阶段和人工修订副本。
4. 原输入复现与当前内容重跑。

### 第 4 组：阶段与分支

1. 四种输出类型与兼容目标查询。
2. 来源/目标状态二次校验。
3. 冲突汇总、批量决定和差异预览。
4. 原子提交、全局撤销/重做和跳转目标。

### 第 5 组：历史记录与收口

1. 统一历史表、筛选和详情检查器。
2. 继续提交、复现、复制草稿和打开目标。
3. 未提交运行的安全清理。
4. 中英文、键盘、浅色/深色、`1280 × 800` 和大型数据回归。

## 11. 自动化验收重点

1. 同一方案草稿连续自动保存不会制造大量逐字撤销记录。
2. 相同版本、相同输入和相同引擎版本得到相同结果及校验值。
3. 运行完成前、预览页面和历史页面都不能写入正式词典。
4. 来源或目标在预览后改变时阻止旧运行提交。
5. 四种输出类型都满足全部成功或全部回滚。
6. 新后代语言保留未参与演化的词，且不留下悬空语素关系。
7. 一次提交只产生一个全局撤销步骤；撤销和重做不重新调用引擎。
8. 旧项目迁移后，旧方案和旧演化证据仍然可读。
9. 5,000 个词条和大量历史记录下，列表滚动、筛选和项目打开时间不明显退化。
10. 浅色、深色、键盘和屏幕阅读器状态均可区分且可操作。

最终建立 `npm run verify:phase7-2`，并包含 Phase 1 ～ 7.1 的适用回归。

## 12. Windows 人工验收清单

### 预览与追踪

- 建立一个会产生变化、无变化、碰撞和错误的运行，统计与逐行结果一致。
- 查看某个词的每一步规则变化，切换窗口再返回后仍停留在该词。
- 分别执行“按原输入重新运行”和“按当前内容重新运行”，确认产生独立记录。
- 关闭网络和 AI 后仍可完成确定性演化预览。

### 阶段与分支

- 分别提交到新历史阶段、已有阶段、已有方言和新后代语言。
- 制造词条冲突，确认系统一次汇总并要求处理后才可提交。
- 在预览后修改来源或目标，确认旧结果被阻止提交。
- 对每种提交执行撤销和重做，检查无残留、无重复、无重新运行引擎。

### 历史记录

- 按方案、类型、状态、日期和关键词筛选。
- 从失败运行查看原因，从成功未提交运行继续提交。
- 从旧版本复制新草稿，确认旧版本未改变。
- 重新打开项目后，历史摘要快速出现，追踪详情可按需读取。

### 主题与窗口

- 浅色和深色模式下检查表格、下拉、警告、禁用态、焦点、弹窗和遮罩。
- 在 `1280 × 800` 下主要按钮、冲突决定和错误说明完整可见。
- 只用键盘完成运行选择、结果检查、输出类型选择、冲突处理和取消弹窗。

## 13. 主要风险与控制办法

| 风险                     | 控制办法                                                               |
| ------------------------ | ---------------------------------------------------------------------- |
| 追踪数据使项目迅速膨胀   | 逐词存储、按需读取；只允许人工清理未提交运行，不自动删除证据           |
| 自动保存污染全局历史     | 以方案为合并键，将连续编辑合并为一个撤销步骤                           |
| 旧预览提交到已变化数据   | 来源和目标双校验值；提交前必须二次验证                                 |
| 新后代语言只生成半套数据 | 应用服务单事务创建；未参与词原样继承；有关联语素时强制一起复制和重映射 |
| 三个窗口状态互相丢失     | 把当前方案、运行、筛选、选中行和滚动位置纳入工作区状态恢复             |
| 大型词典或历史页面卡顿   | 摘要分页、虚拟列表、追踪延迟加载、避免页面初始化读取全部详情           |
| 浅色可用但深色不可用     | 只用语义令牌；把两种主题列为自动截图和人工验收必测项                   |

## 14. Phase 7.2 结项门槛

只有同时满足以下条件，Phase 7.2 才能提交人工验收：

- 三个窗口及与“演化方案”的完整工作流真实可用，没有占位按钮。
- Schema v17、旧项目迁移、失败恢复和备份证据齐全。
- 所有正式提交原子化、可全局撤销和重做。
- 运行可按原规则、原输入和原引擎版本进行复现或明确报告版本不可用。
- `npm run verify:phase7-2` 及此前适用回归通过。
- Windows 外部人工验收清单全部执行并形成报告。
- 未验证项和剩余风险被明确列出，不用“部分完成”宣布结项。
