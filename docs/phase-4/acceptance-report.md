# Phase 4 验收报告

## 当前结论

Phase 4 已于 2026-07-30 通过外部 Windows 人工验收并结项。最后一轮复验确认：

- 10 项词条或语素批量提案可以保存；
- 批量审核决定可以在提交前恢复；
- 演化提案在进入编辑器前经过真实 Lexurgy 校验；
- 后续对话能够读取本会话先前提案，且不会重复生成完全相同的提案；
- 其余 Phase 4 人工验收场景通过。

当前没有已知 P0/P1 缺陷，可以创建 `phase-4.0.1` 结项标签。

## 已实现

- Schema v6：AI 会话、消息、结构化提案和上下文审计；Schema v7 修复已有项目中的旧 5 项提案事务上限。
- Windows 凭据管理器中的 Provider API Key。
- OpenAI、Gemini、DeepSeek 和 OpenAI 兼容服务 Adapter。
- HTTPS、回环 HTTP、同源重定向和凭据脱敏边界。
- 页面、语言和项目三级只读上下文。
- 五类单聚合提案、快照冲突检查、领域验证和显式保存。
- 正式模型设置页、会话侧栏、引用记录、停止请求和提案卡片。
- 侧栏内直接切换已启用的 Provider 和缓存模型。
- 当前页面读取词典、造词、语素、屈折或演化的真实页面数据。
- 单项提案填入正式编辑器后由用户手动保存；多个词条或语素使用批量审核窗口。
- 批量审核以高信息密度可编辑表格呈现，最多接收 50 项提案；保存后当前词典或语素库立即刷新。
- 批量审核首列统一选择“接受/拒绝”，提交前可反复切换；已拒绝项也可恢复为接受。
  表格只使用锁定设计令牌，浅色和深色模式拥有一致的表面、文字与状态层级。
- 提示词、响应解析和 SQLite 原子事务均使用 50 项上限；第 51 项会整笔拒绝，不留下半条回答或半组提案。
- 已发布的 v6 迁移 SHA-384 被自动审计锁定；后续修复只能新增迁移，不能再修改历史迁移。
- 发送期间立即显示用户消息；结构化提案的原始 JSON 不再作为对话正文显示，失败后会清除“正在回答”并重新加载已保存消息。
- AI 造词配置在进入编辑器前统一转换 `members/template/min-max` 等常见别名，并在缺少必要
  类别、模板或音节数量时安全拒绝，不再导致界面崩溃。
- AI 屈折提案只接受受支持的规则树；常见 `prefix`/`suffix` 简写会转换为 Lexurgy 的
  `formula/concat` 结构，无效规则在启动 Sidecar 前即被拒绝。
- 演化提示词已加入经过核对的 Lexurgy 语法约束和示例；提案填入编辑器前还必须通过
  随应用提供的真实 Lexurgy 校验。`Feature voiced(+, -)` 等伪语法会被阻止并显示行列。
- 会话历史会在 18,000 字符安全预算内带回先前提案的类型、摘要、状态和结构，
  “另一个/新的/不同的提案”可以避开本会话已生成内容。
- 应用还会按“提案类型 + 规范化结构”计算稳定指纹；即使模型忽略上下文，完全重复的
  提案也不会再次进入审核。
- 助手回答、引用和提案按同一消息顺序显示。
